# MaxKB4j 编码约定

> 建立于第 3 期结构解耦（2026-08-13）。新代码强制遵守，存量代码逐步迁移。

## 1. Entity 不出入 Controller

- **入参**：`@RequestBody` 一律使用专用 DTO + `@Valid` 校验，字段白名单显式声明；禁止直接绑定 Entity（防 mass assignment）。
- **出参**：一律返回 VO/DTO；禁止返回 Entity 或 Entity 集合。
- Entity ↔ DTO/VO 转换在 Controller 层或专用转换器中显式完成。
- 审计现状（2026-08-13）：全部控制器出参已无 Entity；入参侧第 2 期已完成 23 个端点 DTO 化，第 3 期补齐 `KnowledgeTagsController.addTags`（TagAddDTO）。

## 2. api 模块是叶子契约，互不依赖

- `-api` 模块之间**禁止引入依赖**（含传递依赖）。api 模块只允许依赖：
  - `maxkb4j-common`（经 `maxkb4j-service-api` 父 pom 统一注入）
  - 第三方库（langchain4j、mybatis-plus、reactor、postgresql 等）
- 跨域共享的类型（多个域的 api 契约都要引用的 DTO/枚举/缓存门面）放 `maxkb4j-common`，这是 common 保留业务相关类型的唯一正当理由。
- 仅被单一域使用的契约类型放该域的 api 模块（如 `LlmModelSetting` 在 application-api、`ModelCredential` 在 model-api、`ToolInputField` 在 tool-api、表单字段在 model-api）。
- 服务模块（`maxkb4j-service/*`）可以自由依赖各 api 模块；服务模块之间禁止直接依赖。

## 3. common 的职责边界

- common 只保留：通用工具/异常/R/上下文、跨域共享 DTO（见第 2 条）、跨域静态缓存门面。
- 新增业务类默认放对应域的 api/service 模块，除非满足"多域 api 契约共用"条件。

## 4. 静态缓存门面模式（过渡态）

- `ChatCache`/`SystemCache` 为静态门面 + 可注册 Store（`ChatInfoStore`/`SystemSettingStore`），默认内置实现保证非 Spring 场景可用。
- Spring 启动时由对应 Bean 注册自身实现（application 模块 `ChatInfoCacheService`、system 模块 `SystemSettingCacheService`），Bean 构造器注入缓存实例，测试可替换与断言。
- `AuthCodeCache`、`PublishedApplicationCache` 已完全 Bean 化，直接注入使用。
- 禁止再新增裸静态缓存类；新增缓存一律做成可注入 Bean。

## 5. 弱类型治理

- 持久化/配置 JSON（如触发器 `triggerSetting`）在模块入口处一次性转换为类型化对象（record/DTO），内部逻辑禁止 `getString("魔法键")`。
- 魔法键名收敛为类型化对象上的 `FIELD_*` 常量（前端/持久化契约，勿改）。
- 已落地：`com.maxkb4j.trigger.model.TriggerSetting`（第 3 期）。

## 6. 工作流引用类型化

- 节点引用统一用 `com.maxkb4j.workflow.model.NodeReference(nodeId, field)`；解析走 `NodeReference.parse(...)` 返回 `Optional`，非法引用显式为空。
- `IWorkflow#getReferenceField(List<String>)` 为兼容层（委托 NodeReference），新代码使用 `getReferenceField(NodeReference)` 重载。

## 7. MyBatis 类型处理器

- 类型处理器跟随其处理的实体所在模块；新增处理器包需同步更新 `application.yml` 的 `type-handlers-package`。
- 当前扫描：`com.maxkb4j.common.typehandler`、`com.maxkb4j.application.typehandler`、`com.maxkb4j.model.typehandler`、`com.maxkb4j.tool.typehandler`。

## 8. 单机部署约束（第 5 期确立）

> 按运维决策（2026-08-13），本系统仅以**单实例**部署；多实例/集群方案（Redis 外部化、ShedLock 等）不实施。以下组件依赖进程内状态，水平扩容会导致行为错误，扩容前必须先完成状态外部化：

- **会话与登录态**：sa-token 会话默认存于进程内存，多实例下登录态不共享，请求漂移到其他实例会鉴权失败。
- **内存缓存**：`ChatCache`（聊天上下文）、`SystemCache`（系统设置）、`AuthCodeCache`（验证码）均为进程内缓存，多实例间数据不一致。
- **登录防护**：`LoginAttemptLimiter`（Caffeine 内存计数，key 为用户名+IP），多实例下失败计数被分摊，锁定阈值被稀释。
- **定时任务**：`TriggerScheduler`（触发器调度）无分布式锁，多实例会重复触发同一任务。
- **编译缓存**：`GroovyScriptExecutor` 的脚本编译缓存为进程内 LRU，多实例仅影响性能，不影响正确性。

约束：生产部署形态为单实例（含重启升级窗口）；未来如需水平扩容，须先将上述状态迁移至外部存储（如 Redis，sa-token 有现成集成）并为定时任务引入分布式锁（如 ShedLock）。
